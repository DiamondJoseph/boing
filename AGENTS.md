# AGENTS.md

## Project Overview

Boing is a REST API for tracking games of a journalling RPG (vampires, memories, diaries, prompts).
It has a Spring Boot 4 server (Java 25, Maven, JPA on H2) and a single-page TypeScript client
(`openapi-fetch`, bundled with esbuild) that the server serves as static files. It ships as a
container image and a Helm chart.

## Commands

Run server commands from `server/` and client commands from `client/`.

### Build

```sh
# Server: build the jar without tests or format checks (as CI does)
cd server && mvn install -DskipTests -Dspotless.check.skip=true --batch-mode

# Client: writes src/version.ts (prebuild), type-checks with tsc, then build.mjs clears dist/,
# bundles src/ with esbuild and copies public/ into dist/
cd client && npm ci && npm run build

# Full container image (client + server)
docker build -t boing .

# Helm chart
cd chart && helm dependencies update . && helm package . -d /tmp/
```

### Run

```sh
cd client && npm run build     # the server only serves what is already in client/dist
cd server && mvn spring-boot:run
# then open http://localhost:8080 (API under /api, Swagger UI at /swagger-ui/index.html)

# Container: docker options go before the image name, or they are passed to the app instead
docker run --rm -p 8080:8080 boing
```

The server serves the built client from `client/dist` (see `server/src/main/resources/application.yaml`).
In the container image the client is at `/client` instead. The database is in-memory H2, so data is
lost on restart.

### Test

```sh
# All tests: unit (surefire) + integration (failsafe), as CI does
cd server && mvn verify --batch-mode -Dspotless.check.skip=true

# Unit tests only
cd server && mvn test -Dspotless.check.skip=true

# A single unit test class or method
cd server && mvn test -Dtest=RandomSerializationTest -Dspotless.check.skip=true
cd server && mvn test -Dtest=RandomSerializationTest#testRandomSameAfterSerializing \
  -Dspotless.check.skip=true
```

- Classes named `*IntegrationTest` run only under failsafe (`mvn verify`), never under `mvn test`.
- During `mvn verify` the app starts and `springdoc-openapi-maven-plugin` regenerates
  `server/openapi.yaml`. `APIVersioningIntegrationTest` then checks that file's hash.

```sh
# Client: Vitest with jsdom (src/**/*.test.ts)
cd client && npm test

# Helm chart: helm-unittest suites in chart/tests/ (the plugin is installed in the devcontainer)
helm lint chart && helm unittest chart
```

- Client tests render the real app into jsdom via `start(root, { fetch })` and replace only
  `fetch`, with a `FakeApi` that answers like the server. Assert on what users see and do.
- Chart tests pin `chart.version`/`chart.appVersion`, so release-please bumps don't break them.

### Lint / Format / Type-check

```sh
# Java formatting (google-java-format via Spotless); also runs at the compile phase
cd server && mvn spotless:check --batch-mode
cd server && mvn spotless:apply --batch-mode    # auto-fix

# Client lint and type-check
cd client && npx eslint .
cd client && npx tsc --noEmit

# Repo-wide hooks: YAML/JSON checks, whitespace, gitleaks, Helm values schema
pre-commit run --all-files
```

## Project Structure

- `server/`: Spring Boot app (Maven project, `pom.xml`).
  - `src/main/java/com/example/boing/`: `domain/` (JPA entities), `repository/`,
    `service/` and `controller/`. Each layer has a `generic/` package of shared base classes.
  - `src/main/resources/application.yaml`: Spring config.
  - `src/test/java/`: JUnit 5 tests.
  - `openapi.yaml`: generated API spec. Do not edit it by hand.
- `client/`: TypeScript single-page app.
  - `src/app.ts`: the whole app, started by `start(root, options)`. Hash routes: `#/` (games
    table), `#/new` (new-game form), `#/game/{id}` (game summary). Hash routing is needed
    because the server has no fallback that serves `index.html` for other paths.
  - `src/index.ts`: the bundle entry point; calls `start` on `#app`.
  - `src/app.test.ts`: client tests.
  - `src/api/schema.d.ts`: generated by `openapi-typescript`.
  - `src/version.ts`: generated by the build and gitignored. It is bundled as a second entry
    point because the `Dockerfile` checks the build with `node dist/version.js`.
  - `public/`: `index.html` and `styles.css`, copied into `dist/` unchanged.
  - `build.mjs`: the esbuild build script.
- `chart/`: Helm chart. `values.schema.json` is generated from `values.yaml` by the
  `helm-schema` pre-commit hook (config in `chart/.schema.yaml`). `tests/` holds helm-unittest
  suites (excluded from the package by `.helmignore`; `templates/tests/` is the `helm test` hook).
- `docs/`: `ADRs/` (Architecture Decision Records; copy `-1-template.md` for new ones) and
  `entity_relation_diagram.md` (Mermaid ER diagram of the domain).
- `Dockerfile`: multi-stage build (Node 24 client, Maven/Temurin 25 server, JRE 25 runtime).
- `.devcontainer/`: dev environment: Java 25, Maven, Node 24, Helm with the
  `helm-values-schema-json` and `helm-unittest` plugins, kubectl, minikube, Docker and pre-commit.
  On creation it installs the pre-commit hooks and builds the client. Port 8080 is forwarded.
- `.github/workflows/`: CI (`ci.yml`), release (`release.yml`), PR title check (`pr.yml`),
  release-please (`changelog.yml`), Renovate (`periodic.yml`). Reusable jobs are in `_*.yml`:
  server tests in `_test_java.yml` (run per Java version), client tests and build in
  `_test_client.yml`, chart lint and unit tests in `_test_chart.yml`.

## Code Style & Conventions

- Java: Spotless enforces google-java-format, sorted imports, no wildcard or module imports,
  no unused imports, and Cleanthat refactors. Run `mvn spotless:apply` before committing.
- Adding a domain entity means adding the matching layers:
  - `domain/<Name>.java` extends `Persistable`.
  - `repository/<Name>Repository.java`.
  - `service/<Name>Service.java` extends `ImmutableService` or `MutableService`. It declares
    nested `New<Name>` (and `<Name>Update` for mutable services) request types.
  - `controller/<Name>Controller.java` extends `ImmutableController` or `MutableController`,
    mapped at `/api/<name>`.
- Request records mark required fields with `@JsonProperty(required = true)`.
- Update `docs/entity_relation_diagram.md` whenever entity relationships change.
- TypeScript: strict `tsconfig.json` (`noUncheckedIndexedAccess`,
  `exactOptionalPropertyTypes`, no unused locals or params). ESLint uses the recommended JS and
  typescript-eslint configs. Use `openapi-fetch` with the generated `paths` types for API calls.
- Client UI: no framework. Build the DOM with the `el()` helper in `app.ts` and set user text
  via `textContent`/children, never `innerHTML`. Async page renders take an `isCurrent()` check
  so a slow response cannot overwrite a newer page.
- CSS: colours are custom properties on `:root` in `styles.css`. Reuse them rather than adding
  literal colours.
- Spelling: British English in prose, comments, identifiers and UI text, except where a language,
  API or tool requires otherwise (e.g. CSS `color`, Kubernetes `autoscaling`, Maven `license`).
- Keep the Java (25) and Node (24) versions in sync between `Dockerfile`,
  `.devcontainer/devcontainer.json` and the CI workflows. Keep the Helm plugin versions in sync
  between `.devcontainer/Dockerfile` and the workflows that install them.
- Commits and PR titles follow Conventional Commits (`feat`, `fix`, `docs`, `test`, `ci`,
  `refactor`, `perf`, `chore`, `revert`). Use `feat!:` for breaking API or database changes.
  release-please builds `CHANGELOG.md` from these.

- After an API change, run `mvn verify` in `server/` (regenerates `openapi.yaml`), then
  `npm run generate:api` in `client/` to regenerate `src/api/schema.d.ts`.
- Service `createAndSave`, `update(id, ...)` and `delete` are `@Transactional` (in the
  `generic/` base classes), so a failure part way through, such as a refused child update in
  a game PATCH, rolls back everything the request saved. Keep multi-step writes inside them.

## Gotchas

- The `Game` constructor rejects a new game unless it has exactly 3 skills, exactly 3
  resources and at least 3 people (`GameService` turns this into a 400). The new-game form
  mirrors these limits in its `listSection(...)` calls. Keep the two in sync.
- Operation IDs for the generic controllers are set by `controller/generic/OperationIdCustomizer`
  from the controller name: `create<Entity>`, `list<Entities>`, `get<Entity>`, `update<Entity>`,
  `delete<Entity>`. Add irregular plurals to its `IRREGULAR_PLURALS`. Other controllers name
  their operations with `@Operation(operationId = ...)`.
- If creating a game fails, the client saves the form to `sessionStorage` and restores it the
  next time the form opens, until the game is created or the draft is discarded.
- The `Vampire` response field is misspelt `intialDescription`, while the request field
  (`NewVampire`) is `initialDescription`. Fixing it is a breaking API and database change.
- `GET /api/game/{id}` returns 200 with a `null` body for an unknown id, not 404.
- `POST` endpoints return 201 even though `openapi.yaml` documents 200.
- npm warns that it skipped esbuild's install script. That is harmless: the binary comes from a
  platform-specific optional dependency.

## Testing Rules

- Tests must exercise real code paths. Do not fake, mock or stub anything just to make a
  test pass. Never hard-code expected outputs to match broken behaviour.
- Never delete, skip, `@Disabled` or weaken a failing test to get a green build. Fix the code,
  or report the failure and explain it.
- Do not bypass checks with `-DskipTests` or `-Dspotless.check.skip=true`, except in the build
  commands listed above.
- Changing the API changes `server/openapi.yaml` and breaks `APIVersioningIntegrationTest`.
  Updating `EXPECTED_HASH` is only acceptable when the API change is intended. Call it out
  explicitly, since it may need a `feat!:` title.
- New behaviour needs tests. Name tests that need the running app or generated artifacts
  `*IntegrationTest` so failsafe picks them up.
- Before declaring work done, run `mvn verify` and `mvn spotless:check` in `server/`. Run
  `npm test`, `npx eslint .` and `npm run build` in `client/` if you touched the client, and
  `helm unittest chart` if you touched the chart.

## Workflow & Boundaries

- Small, single-file changes: make them directly, then run the relevant checks.
- Multi-file changes, such as a new entity across all layers, API changes or schema changes:
  outline the plan first and keep commits atomic.
- Significant architectural decisions get a new ADR in `docs/ADRs/`.
- Never do these without asking first:
  - Commit or push to `main`, create releases or tags, or edit `CHANGELOG.md` and
    `.release-please-manifest.json` (release-please owns them).
  - Make breaking API or database changes, or update the OpenAPI hash.
  - Add, remove or upgrade dependencies (Renovate manages version bumps).
  - Change CI workflows, the `Dockerfile`, the devcontainer, or Helm chart defaults.
  - Hand-edit generated files (`server/openapi.yaml`, `client/src/api/schema.d.ts`,
    `chart/values.schema.json`).
  - Commit secrets or credentials. gitleaks runs in pre-commit and CI.
